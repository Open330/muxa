## 측정

### 운영 데이터의 조회 비용

운영 소켓에 읽기 전용 요청을 보내 같은 all 범위를 비교했다. 각 경로를 별도로
읽었으므로 그 사이 새 메시지가 추가되는 정도의 차이는 있을 수 있다. 본문은
검증 파일에 보관하지 않았다. 바이트는 newline을 포함한 **내부 IPC 응답**이며
모델 입력 토큰이나 사용자에게 청구되는 비용이 아니다.

| 조회 경로 | 행 수 | 페이지 | IPC 응답 바이트 |
|---|---:|---:|---:|
| 보드의 기존 전체 이력 preview | 2,356 | 5 | 5,200,080 |
| queued 메타데이터 | 17 | 1 | 21,981 |
| claimed 메타데이터 | 22 | 1 | 35,034 |
| 새 보드 조회 합계 | 39 | 2 | 57,015 |

변경이 없는 동안은 revision 구독을 통해 위 목록 조회 자체를 생략한다. 이 동작은
mock IPC 테스트에서 추가 요청이 발생하지 않는지 확인한다. 이미 실행 중인 예전
watch 프로그램에는 새 바이너리 설치만으로 이 변경이 적용되지 않는다.

실제 watch를 별도 PTY에서 45초 관찰했을 때, 안정화 뒤 25초 구간의 목록 조회는
0회였다. 다만 이 검증에서 보드 시작 시 숨겨진 수신함이 전체 preview를 한 번
읽는 추가 비용을 발견했다. 숨겨진 수신함은 room context와 미완료 메타데이터만
읽도록 추가 수정했다. 사람에게 응답이 필요한 건수와 빠른 전송 경로는 유지하고,
수신함을 실제로 열었을 때 이력 preview가 로드되는지도 별도 테스트로 확인한다.

발신자 위치를 알아내려고 읽던 전체 레지스트리는 같은 시점에 124,683바이트,
단일 세션 조회는 1,546바이트였다. 최종 구현은 이 별도 조회도 하지 않고 후속
협업 요청의 대화 ID를 데몬에서 해석하므로 추가 발신자 조회 RPC는 0회다.

### 대량 claim의 반환 누락

격리 IPC 테스트에서 Fleet 수신함이 40건을 claim한 뒤 최종 응답을 32건으로
자르는 문제를 재현했다. 표시되지 않은 8건도 Claimed가 되어 있었다. 이제
`collaboration_inbox_limit_v1`을 확인한 클라이언트만 한 번의 원자적 claim으로
최대 32건을 변경·반환한다. 나머지 8건은 Queued를 유지한다. 다음 배치는 이미
claim한 재조회보다 아직 Queued인 요청을 우선한다. 기존 primary 보호 조건을
제한 전에 적용하며, 일반 inbox와 정확한 ID 하나의 claim은 기존 계약을 유지한다.

구형 데몬에는 안전하지 않은 unbounded claim으로 fallback하지 않는다. capability
확인 단계에서 거절해 실제 claim 요청 자체가 전송되지 않는지 검증한다. 이 동작은
운영 에이전트의 실제 대기 요청을 대량 claim하지 않고 격리 테스트로 검증한다.

## 남은 한계와 후속 기준

- **터미널 입력과 DB는 하나의 원자적 트랜잭션이 아니다.** PromptWritten 뒤에
  수신 TUI가 입력창을 잃은 경우와 입력창을 그대로 가진 경우를 영속 DB만으로
  구분할 수 없다. 화면의 일부 문자열만 보고 자동 재전송하면 중복 작업을 만들 수
  있다. 기존 claim/Enter 복구를 유지하며, 이 경우까지 정확히 한 번 실행된다고
  보고하지 않는다. 별도의 수신 확인 프로토콜을 도입할 때 다뤄야 한다.
- **알림을 받은 뒤 claim하지 않은 수신자가 사라진 경우** 자동 재배정하지 않는다.
  알려진 Error/Stopped는 기존 interruption 경로로 처리하지만, 레지스트리 행의
  부재만으로 프로세스 종료를 추론하지 않는다. 향후 명시적 stranded 진단·인계는
  실제 프로세스 종료 근거와 작업 권한을 함께 확인하는 방식이어야 한다.
- **SQLite 연결 재사용은 이번 변경에 포함하지 않았다.** 현재는 작업마다 파일을
  열고 스키마·권한을 확인한다. 재사용하려면 파일 삭제·교체 시 이미 열린 이전
  inode에 성공적으로 쓰고도 현재 DB에는 반영되지 않는 문제를 막는 fence가
  필요하다. 실패 의미를 바꾸는 단순 connection cache를 넣지 않았다.
- **구형 데몬의 query 미지원 fallback**은 전체 이력을 받을 수 있다. 현재 데몬의
  서버 쪽 필터링·제한은 검증하지만, 구형 서버의 전송량까지 줄였다고 주장하지 않는다.
- **실행 중인 예전 watch 및 원격 relay**는 각각 새 실행이 필요하다. 운영 중인
  다른 세션이나 SSH 연결을 검증 목적으로 강제 종료하지 않는다.
- Linux에서 Rust/IPC 검증을 수행한다. macOS 앱 빌드와 실제 원격 SSH 장애
  주입은 이 환경의 검증 범위에 포함하지 않는다.
